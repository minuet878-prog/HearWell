用這個格式寫 PR 說明。改編自 Matt Pocock 的 `pr` skill（https://github.com/mattpocock/skills），依我的工作流調整。

## 寫在哪裡

寫進 `docs/reviews/〈規格檔名〉_pr.md`，對話裡只放檔案路徑。我會自己貼到 GitHub 開 PR。不要自己開 PR、不要 push。

## 語言

- PR 標題用英文，跟 commit message 一樣是 Conventional Commits 格式。
- 內文用繁體中文，用專案的用語（CLAUDE.md、規格檔裡的名詞）。不要開場白，句子要短。

## 範本

```
## 摘要

〈一兩句話：改了什麼、為什麼。附上規格檔連結。〉

〈一張最小的圖，見下方「摘要怎麼畫」〉

## 證據

- **修改前：**〈截圖／錯誤輸出／失敗的測試〉
  **修改後：**〈截圖／正確輸出／通過的測試〉
- 測試結果：〈通過／失敗數〉
- 驗收條件：〈規格檔第 5 節，全部打勾／哪幾條例外〉

## 合併風險

**門：**單向門／雙向門
〈一句話說明〉

**影響範圍：**〈一個詞，例如：版面、API、資料庫、全站〉
〈可能波及的地方〉
```

## 摘要怎麼畫

挑**最小**、能把重點講清楚的一種就好，通常一到兩種，不要全用：

- **邏輯或流程** → 虛擬碼（pseudocode，用接近口語的方式寫程式邏輯，不必能執行）
- **一個請求經過哪些函式** → 呼叫樹（縮排表示誰呼叫誰）
- **畫面結構** → 元件樹（React 元件或 Django template 的包含關係）
- **檔案搬動或大範圍重構** → 淺層的檔案樹
- **重點是「改了什麼」** → 用 `diff` 格式（`+` 新增、`-` 刪除），套在上面任何一種圖上

例：

```
 POST /api/submissions/
   SubmissionSerializer.validate
+    檢查題數是否與問卷一致
   Submission.objects.create
   Answer.objects.bulk_create
```

## 證據的等級

- **S 級：截圖。** 有畫面變動時優先。可以用 e2e 測試在 `e2e-artifacts/` 產生的截圖，或請我手動截。
- **A 級：執行結果。** 測試輸出、指令輸出。寫出「哪個測試原本失敗、現在通過」，用虛擬碼描述那個測試在驗證什麼。
- 沒有修改前／後可以對照的（例如純新增功能），就寫「新增前：沒有這個功能」，修改後附上證據。

## 合併風險怎麼判斷

- **雙向門**：做錯了可以退回，例如改畫面、改文字、新增不影響舊資料的 API。退版就好。
- **單向門**：做了就很難回頭，例如：
  - 會改動或刪除既有資料的 migration
  - 改了 fixture 裡已上線的題目（`build.sh` 每次部署都會 `loaddata`）
  - 改了分級門檻（`scoring.THRESHOLDS`），會回溯改寫歷史分級
  - 改了 API 的回傳格式，而前端已經在用
- **影響範圍**要把可能性都想過：版面跑掉、手機版、字級縮放、65 歲以上使用者的操作、上一頁、PWA、正式資料庫。
