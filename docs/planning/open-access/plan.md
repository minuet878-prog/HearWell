# 聽伴 開放階段規劃：降低進入門檻

給 Claude Code 的起點文件。照 `CLAUDE.md` 的流程走：每一項先拷問、寫規格、拆票、先寫測試、審查、驗收。
這份文件裡的「已決定」是拷問的起點，本人可以在拷問時推翻；「待決定」請在拷問階段問本人。

## 背景

正式站（tingpal.tw）還沒有真實使用者。目前要先註冊、同意才能作答，而且只能用帳號密碼。
這個階段的目標只有一個：讓第一次來的人更容易進來，並且量得出來有沒有變容易。

### 跟全站改版怎麼排（2026-11-13 本人決定）

原本寫「排在全站改版第 2 階段之前」，改成**拷問同步、實作錯開**：

- 開放階段的拷問與寫規格現在就做，跟 #478（照顧旅程待辦）、#484（聽損模擬）的實作同時進行。
- 第 1 項的程式等 #478 合併回 `main` 後才開工。原因：沒登入與登入後的首頁是同一個
  `index.html`；兩邊都要新增 migration，同時做會撞號。
- #484 不存資料、不用登入，跟開放階段不衝突，照原排程做。
- 開放階段第 1–3 項做完，再回到第 2 階段的便當格＋聽力護照。
- 「怎麼戴」（第 3 階段，還沒寫規格）的位置還沒決定。
- 隱私權說明若要升同意書版本，會跟 ADR 0050 給情境日記的第 5 版衝突，拷問時一起決定。

| 順序 | 項目 | 為什麼排這裡 |

| 3 | LINE 登入 | 對長輩最有用，但有 LINE 內建瀏覽器等額外問題，放在架構穩定之後 |
| 4 | 看漏斗數字 | 用第 1 項留下的月計數，決定後面做什麼 |

每一項各開一份母規格。

### 第 1 項跟第 2、3 項怎麼排（2026-11-13 本人決定）

**拷問一起、實作分開**：

- 第 2、3 項的拷問與寫規格現在就做，不等第 1 項驗收；第 1 項的程式反正要等 #478 合併。
- 實作照順序：第 1 項驗收後做 Google，Google 驗收後做 LINE。原因：登入要本人先到兩家後台
  建頻道、拿金鑰，還要實機測 LINE 內建瀏覽器；綁在一起會拖住第 1 項，而且碰到權限、要交叉審查，
  diff 太大容易漏看。
- 第 1 項的保存不管用哪種方式註冊都要能接上：同意之後就送出瀏覽器裡的訪客結果，
  之後 Google／LINE 只多一個入口，不用改保存流程。
- 第 4 項的一個月從三項都上線後開始算，免得還沒有 LINE 登入時，保存次數偏低。
- 拷問前不實機測（網站還沒有第三方登入，測不到），照最壞情況設計（[登入研究](login-research.md)第 3 節）：
  - 假設 Google 在 LINE 內建瀏覽器裡會被擋：在那裡不顯示 Google 按鈕，只放 LINE 和帳號密碼，
    另外放「用 Safari／Chrome 打開」。
  - 假設 LINE 跟 Safari／Chrome 的資料不共用：訪客結果頁寫清楚換瀏覽器就看不到這次結果。
  - 驗收時由本人用 iPhone 從 LINE 裡實機走完一次登入，再確認這兩個假設。

## 第 1 項：免註冊先篩檢

### 現有可以沿用的零件
- `frontend/src/draft.js`：未完成作答存在瀏覽器 localStorage，7 天，帶 userId 與收據編號。
- `POST /api/submissions/`：收據編號防重複，唯一性已經只在同一個帳號底下檢查。
- 問卷定義檔（ADR 0005）：計分與分級都向定義查。
- `@health_data_page` 與 `test_standards.py` 的檢查（#182）。
- `QuestionLog`／`QuestionLogMonth`：清掉明細、只留月計數的做法（ADR 0034）。

### 已決定
1. 只開放 HHIE-S 與 HHIA-S。
2. 訪客的作答只存在他自己的瀏覽器，伺服器不寫進資料庫。
   伺服器提供一個「只算分、不儲存」的入口，照問卷定義回傳分數與分級。
3. 訪客看到完整結果，不遮內容逼註冊。結果頁多一個入口：「註冊就能保存這次結果，之後可以比較」。
4. 認領：從訪客結果頁走到註冊、同意完成後，用原本的寫入 API 送出，沿用同一個收據編號，
   成功後清掉瀏覽器裡的訪客作答。`Submission` 一律在 `Consent` 之後才建立，`user` 欄位不改。
5. 訪客作答用自己的儲存鍵，不跟登入使用者的草稿共用 `DRAFT_PREFIX`
   （`loadDraft` 會刪掉 userId 不符的草稿，兩種資料規則不同）。
6. 絕不自動把訪客作答掛到帳號上。
   - 從訪客結果頁開始的註冊：視為本人，同意後直接保存。
   - 登入既有帳號時瀏覽器裡有訪客作答：先問「要把這次結果存到這個帳號嗎？」，選「不要」就清掉。
7. 訪客結果頁有「清除這次結果」按鈕；訪客作答最多留 7 天。
8. 訪客結果頁算健康資料頁面：禁止快取，`test_standards.py` 的檢查要涵蓋不用登入的這一頁。
9. 「只算分」的入口要有速率限制（目前全站沒有 throttle 設定）。
10. 成效只留匿名月計數：訪客完成次數、其中後來認領的次數。不存明細、不存 IP。
11. 隱私權說明補上「未註冊時只計算、不儲存，作答留在您的瀏覽器」。

### 待決定
- 訪客入口放哪：未登入首頁的主要按鈕直接開始，還是維持「登入／註冊」為主？
- 推薦精靈問的年齡組別，註冊時要不要帶進去？
- 訪客作答頁的「有戴／沒戴助聽器」照問嗎？
- 訪客結果頁的「建議下一步」推什麼？
- 註冊途中放棄再回來，訪客結果從哪裡回得去？
- 速率限制的數字，以及被擋下時畫面寫什麼。
- 隱私權說明這次的修改，要不要升同意書版本？
- 月計數的「後來認領」怎麼算，才不需要在伺服器記住是哪一次訪客作答？

### 驗收重點
- 沒登入做完 HHIE-S，資料庫沒有新增任何 `Submission`、`Answer`。
- 註冊並同意後，我的紀錄出現那一筆，分數與訪客結果頁相同；重送不會變兩筆。
- 用另一個既有帳號登入同一個瀏覽器，沒有按「要」之前，那個帳號沒有多出紀錄。
- 按「清除這次結果」後，返回鍵看不到結果。
- e2e 新增一條「訪客先做、再註冊認領」的路線。

## 第 2、3 項：Google 登入、LINE 登入

兩項共用同一套架構，所以決定寫在一起；實作分兩批，Google 先、LINE 後。

### 已決定
1. 帳號密碼登入保留，第三方登入是多一個選擇，不是取代。
2. 只向對方要「辨識這個人」所需的最少資料。
   - 存：是哪一家、對方給的使用者代號。
   - 不存：大頭貼、好友名單、存取權杖（登入完成後不需要再呼叫對方）。
   - LINE 不申請 email 權限（那需要另外送審），所以 LINE 註冊的帳號可以沒有 email。
3. 絕不依 email 自動合併帳號。
   - 第三方登入的代號沒見過 → 建立新帳號。
   - 想把 Google／LINE 綁到既有帳號 → 必須先登入那個帳號，再到帳號設定裡按「連結」。
   - Google 回傳的 email 跟某個既有帳號相同時：不合併、不登入那個帳號，畫面請他用密碼登入後再連結。
   理由：認錯人等於把健康資料給錯人，而且很難事後發現。
4. 第一次用第三方登入的人，一樣要走同意書，同意之前不能存任何健康資料。
5. 第 1 項的訪客認領要能接上：訪客結果頁 →「用 Google／LINE 註冊」→ 跳出去再回來 → 同意 → 保存。
6. 帳號設定頁顯示已連結的登入方式，可以解除連結；但不能解除到一種登入方式都不剩。
7. 資料匯出要包含已連結的登入方式；刪除帳號時連結一併刪除。
8. 兩家的金鑰放環境變數。沒設定某一家時，那一家的按鈕不顯示，網站照常啟動。
9. 隱私權說明新增：用 Google／LINE 登入時，我們從對方拿到什麼、沒拿什麼。
10. 測試不連真的 Google／LINE：用假的對方回應測完整流程，真機只在驗收時由本人操作。
11. 不做 Apple 登入（要每年付費的開發者會員）、不做 Facebook 登入。
12. 不做 LINE 推播提醒（另一項，之後再排）。

### 請 Claude Code 先研究再提案（寫進研究文件，重要的寫 ADR）
- 用現成套件（例如 django-allauth）還是自己照 OpenID Connect 流程實作？
  比較：維護成本、能不能只拿最少資料、跟現有 `User`／`Consent`／登入頁的相容性、對測試的影響。
- 安全項目各自怎麼處理：`state`（防偽造回呼）、`nonce`、PKCE、回呼網址完全比對、ID token 驗證。
- LINE 內建瀏覽器：從 LINE 裡點開連結時，網頁開在 LINE 自己的瀏覽器，不是 Safari／Chrome。
  - 那裡的 localStorage 跟 Safari 不共用，第 1 項的訪客作答會不會因此認領不到？
  - 「加到主畫面」在那裡不能用，要怎麼引導？
- Google 的 OAuth 同意畫面在「測試中」與「已發布」狀態下，對一般使用者的限制。
- 兩家目前的費用與用量限制，附官方來源連結（本人的理解是兩者登入都免費，請確認）。

### 待決定
- 登入頁與註冊頁上，三種登入方式怎麼排？哪一個是主要按鈕？（長輩優先）
- 只有 LINE、沒有 email 也沒有密碼的帳號：LINE 帳號不見了怎麼救回？要不要強制補一個 email 或密碼？
- 沒有 email 的帳號，現在哪些功能會壞？（忘記密碼、通知信、之後的重測提醒；自助重設密碼見 #355）
- 第三方註冊的人，使用者名稱怎麼產生、畫面上稱呼他什麼？
- 生日／年齡組別：第三方註冊後在哪一步問？
- 解除連結時要不要再確認一次身分？
- 隱私權說明的修改，要不要升同意書版本？
- 月計數要不要分「用哪一種方式註冊」？

### 驗收重點
- 用 Google 第一次登入：建立新帳號、走同意書、能作答並保存。
- 用同一個 Google 再登入：回到同一個帳號，不會多出第二個。
- Google 的 email 跟既有密碼帳號相同：沒有被合併，也沒有登入那個帳號。
- 既有帳號連結 LINE 後，用 LINE 登入進到的是同一個帳號、同一批紀錄。
- 訪客做完問卷 → 用 LINE 註冊 → 同意 → 那一筆出現在我的紀錄。
- 回呼被竄改（`state` 不符、重放舊的回呼）會被拒絕。
- 某一家金鑰沒設定：按鈕不出現，其他功能正常。
- 本人用 iPhone 從 LINE 裡點開連結，實機走完一次登入。

### 需要本人自己做的事（Claude Code 做不到）
- 在 Google Cloud 建立 OAuth 用戶端，填回呼網址，取得金鑰。
- 在 LINE Developers 建立 LINE Login 頻道，填回呼網址，取得金鑰，並把頻道從「開發中」改成「已發布」。
- 把金鑰放進 VPS 的 `.env` 後重啟服務。
- 規格裡請列出每一步要填的確切值（回呼網址、要勾的權限）。
